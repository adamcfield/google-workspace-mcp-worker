## 1.6.0 — 2026-09-23

### Docs: edit one section, set paragraph spacing, work with comments

A QA session on the JEV QA build found Docs reading good but writing coarse: every edit meant regenerating the whole document as HTML and replacing it, which gave poor control over spacing (paragraphs kept ending up against tables) and risked detaching existing comments from their text; and comments had no tool at all, only a raw `google_api_request` call. Five tools and one description change answer that. `tools/list` grows from 163 to 168 tools.

- **`docs_replace_section`** replaces the body under a heading — up to the next heading of the same or higher level, or the end of the document — with plain text. It reads the document once and writes with ONE `batchUpdate` guarded by the revision it read (`requiredRevisionId`), so a document that changed in between is refused rather than edited at stale indexes. Only the section is touched: the heading and everything outside it are left as they are, so comments anchored elsewhere stay where they are. The Docs API's own rules are respected rather than tripped over: a table inside the section is removed whole, never split; a section at the end of the document keeps the body's final newline, which Docs refuses to delete; an empty section, or a heading that is the last paragraph, gets a fresh paragraph. New text is `NORMAL_TEXT` without bullets even where it would otherwise inherit the next heading's style. Characters the Docs API strips from inserted text (control characters U+0000–U+0008 and U+000C–U+001F, and Private Use Area glyphs such as the U+F0B7 bullets Word pastes) are removed before any index is computed, so the style range and the returned end index match what Google stored instead of reaching into the next heading; `strippedChars` says how many went. The heading is matched exactly and case-sensitively; when it is missing, the error lists the document's headings (the first 25, then a count; each JSON-quoted, cut at 80 characters and labelled as document text, not instructions) and points out a case-only near miss; when it repeats, or exists only at another level than `heading_level`, the error lists the occurrences with their level and index, capped and quoted the same way (the first 25, then a count), and `occurrence` (1-based) or `heading_level` picks one. `include_heading` replaces the heading paragraph as well. Returns the section's old range, the characters inserted and where the section now ends.
- **`docs_update_paragraph_style`** sets space above/below (points), line spacing (percent), alignment and named style on an index range or on the body of a section found the same way. The `fields` mask lists exactly the properties passed — a field named in the mask without a value is reset by Google, which is how a hand-built raw request silently wipes other spacing. In section mode it styles runs of paragraphs and leaves table cells alone. The description says where room below a table comes from: `space_above` on the paragraph right after it.
- **`docs_list_comments`**, **`docs_create_comment`**, **`docs_create_reply`** use the Drive v3 comments and replies endpoints, always with the explicit `fields` parameter those endpoints require, on the `drive` scope `docs_export_document` already used — no new scope, so no reconnect. The list returns id, author, content, the quoted text, resolved, created time and a reply count (deleted replies not counted), paginates with `page_token`, can include the replies, and puts the provenance notice before the comment text because comments are third-party content. `docs_create_reply` with `resolve: true` sends `action: "resolve"`. The create description states the Google limitation plainly: comments created through the API are not anchored to a text range in Google Docs and appear as document-level comments.
- **`docs_insert_table`** already filled its cells from a 2-D array; its description now says so up front ("no need to build HTML"), because the QA session built tables as HTML instead.
- **Tool selection.** Route blocks (English and Hebrew) for the five tools, lexicon entries for their resources, and mutation-gate cues so a request reaches them. The cues matter because the gate is the only way a writing tool enters a selection, and it narrows its pool to the verbs it read before it ranks anything: a comment request has to read as *create* itself, or the reply tool is never in the pool. Before these cues, "reply to the comment" read only as *send* (mail tools), "mark the comment as resolved" only as *modify* (which offered the section and style tools instead of `docs_create_reply`), "respond to the comment" only as *rsvp*, and "comment on the proposal doc that the numbers are wrong", "justify the paragraphs in the document", "center the title in the doc", "double-space the document" and "תיישר את הכותרת למרכז במסמך" reached no writing tool at all. They now reach `docs_create_comment`, `docs_create_reply` and `docs_update_paragraph_style`, in both languages.
  The gate's first rule is that a request which asks for no change gets no writing tool, and its cues are word sets matched in any order, so each new cue is tied to the words that make it a request rather than a question. "Rewrite", "reword" and "redo" count only next to "section" or "doc"/"document" (alone they are how people ask for an answer to be reformatted or a search repeated). "Comment on" counts only when what to say follows ("that", "saying"), because "show me the comments on the design doc" contains the same two words. Alignment counts only with the text it aligns ("justify the paragraphs", "center the title", "align the text"; bare "justify", "center" and "align" also mean give reasons, a cost center and agree). Space counts only as "spacing", or as a change in the amount of space next to a paragraph, table or heading ("add more space below the table"). A bare "more space" matched "show me more messages from the team space", since "space" is the Chat and Meet noun, and "space above the table" matched "how much space above the table is there". The Hebrew formatting cues are imperatives tied to what changes ("תגדיל ריווח", "תיישר את הכותרת"). A bare "להגדיל" or "ליישר" is also how a budget question ("בכמה להגדיל את התקציב בגיליון") or a how-to question ("איך ליישר טקסט במסמך") is asked. For the same reason, the spacing tool's route text and lexicon entry say "spacing" rather than "space …", and name no position: the router reads each word of a phrase on its own, so "spacing above", "spacing below", "above or below", "רווח מעל", "רווח מתחת" and "ריווח שורות" (line spacing — שורות is also "rows") made it a match for Sheets row requests ("insert two rows above row 5 in the sheet and fill in the right names", "move the rows below row 5 up in the sheet", "תשנה את השורות"), where the gate offered it in place of `docs_insert_text` or `tasks_move_task`. Those requests get exactly the writes `release/1.6` gave them again (plus `sheets_batch_update_spreadsheet` on a row cue). The requests those position words reached — "add more space above the heading in the document", "reduce the space below the heading", "add more space below the table", "תקטין את הרווח מתחת לטבלה במסמך" — are read by the gate instead, as a phrase: a change verb, the space, a position and the heading, title, table, paragraph or section it is next to, in that order, in English or Hebrew (`OWN_EVIDENCE_PATTERNS` in `src/routing/gate.ts`). A match admits `docs_update_paragraph_style` on top of the ranked answer, the way a row cue admits `sheets_batch_update_spreadsheet`, and only where the request aims at Docs or at no product (the matched "space" is not counted as a Chat space). So a row request (no space), "add the table to the Engineering space" (no position next to an element), "add space below the table in the spreadsheet" (aimed at Sheets) and "how much space is above the heading" (no change verb) get no spacing tool; the pattern is read over the gate's capped text. Over 480 spacing requests (8 English change phrases × space/spacing × 6 positions next to a heading, table or paragraph, bare or "in the doc/document", and 4 Hebrew verbs × רווח/ריווח with and without את × 6 positions, bare or "במסמך"), the spacing tool is reached on all 480; the source branch reached 444, and the tree before this reading 326. "תוסיף רווח מתחת לטבלה במסמך" reaches it too. The comment tools' route text no longer uses "whether", which had pulled `docs_create_reply` into "check whether I am free … and book a call". `docs_append_text` gains the keyword "add them to the document", so the comment tools do not push it out of that phrasing (benchmark case J29). The router's shared word lists change in one place: YouTube's service words lose the bare "comments" (see the gate bullet below). The Docs group hint returned by `google_list_tools` mentions sections, spacing and comments. Routing accuracy is unchanged (dev 70/72, holdout 21/25). The tool-selection benchmark still has 100% mutation recall and 0 forbidden selections.

"Did anyone leave a comment on …", "what was the answer to the comment on …" and "how many comments did I resolve last week" get the comment tools first. "How do I align the text in the doc" gets the style tool and the Docs replace tools. The formatting cues are not tied to a document either, so "does the email have double spacing", "why does the email text align right" and "reduce spacing in the email" get `docs_update_paragraph_style` and the recoverable Gmail and Chat update tools (`gmail_untrash_message`, `gmail_update_draft`, `chat_update_message`). In each case a question and a request use the same words in a different order, and the gate does not look at order. None of these is offered an irreversible tool: see "Its own verb" below.
- **Mutation gate: the target of an irreversible tool is judged per tool.** The gate's second rule offers an irreversible tool without a `confirm` argument only when the request names a target, and "names a target" was one flag for the whole request: any service, any resource, any pasted object. Adding "comment", "comments", "reply", "section"/"chapter" and the spacing and alignment words to the resource lexicon therefore widened what an unaimed delete could reach: "delete the comment", "remove the section", "remove the spacing", "clear the section", "end the comment" and their Hebrew forms ("תמחק את ההערה", "תסיר את הסעיף", "תמחק את כל ההערות") were refused on `release/1.6` and were offered `drive_delete_file`, `calendar_delete_event`, `sheets_delete_sheet`, `contacts_delete_contact`, `chat_delete_message`, `sheets_clear_range` or `meet_end_conference` here — none of which acts on a comment or a section. ### `sheets_audit_spreadsheet`: errors vs warnings, one finding per cell, fewer false alarms

A QA session audited a finished budget model and got **0 errors next to 43 "inconsistent formula" and 63 "range stops before data" warnings** — almost all false alarms on totals, headers and fixed-size ranges — with some findings listed twice and every long formula printed in full. The real result, "nothing is broken", was buried. This change makes the warnings mean something and the reply short.

- **Errors and warnings; `ok` now means "no errors".** Error cells and references to missing sheets are *errors*: the sheet shows a wrong value right now. Inconsistent formulas and ranges stopping before data are *warnings*: heuristics about how the model is built. `ok` used to mean "no findings of any kind", which a healthy model with a quarterly-subtotal column could never reach. New top-level `errorCount` and `warningCount` count *cells*, so `"ok": true, "errorCount": 0, "warningCount": 3` reads as healthy with notes, and a `#REF!` that names a missing sheet is one error, not two. `errors` is still the list of error cells (`{ items, truncated }`, capped by `max_findings`), as before and as in the Sheets write tools' verification, where `errors` is a list too. Nothing in this repository read `ok`; a caller that relied on the old meaning should test `errorCount === 0 && warningCount === 0`.
- **`detail`: `summary` (default) or `findings`.** The summary carries the counts, every error cell (capped by `max_findings`), and the 10 likeliest-real warnings of each kind — the break in the longest fill-down, and the ranges *fewest* cells short of their data, because a total one row short is the classic slip and must not be crowded out by ranges that leave out long runs — with `truncated` saying how many more exist and a `note` pointing at `detail=findings`, which lists the rest in sheet order. Both modes cap each category at `max_findings`, as before. Errors are never cut to 10: they are the signal. A claude.ai connection added before this change does not see the new parameter until the connector is re-added, and gets the summary.
- **One finding per cell per category.** Three things listed a cell more than once: a formula reading the same range twice (`=IF(SUM(B2:B9)=0,0,SUM(B2:B9))`), a formula reading two short ranges (`=SUMPRODUCT(A2:A9,B2:B9)`), and overlapping `ranges`, whose overlap was loaded — and reported — twice (it also split fill-down runs, so a real break inside the overlap could go unreported). A range finding now lists each short range of its formula once (at most 10, see **Output fields**); an inconsistent formula that breaks both its column and its row pattern is one finding with both.
- **Long formulas are clipped** to 117 characters plus "…" in every finding, including the neighbour quoted in `differsFrom`; `formulaLength` gives the real length.
- **Fewer false warnings.** Each rule is explained in a code comment in `src/tools/sheets-analysis.ts` and tested on a realistic layout in `tests/sheets-analysis.test.ts`:
  - *Totals.* A SUM/SUBTOTAL/AVERAGE/… of the block before or after it in its own column or row — the Total row under a fill-down, the Total column at a row's right edge, a quarterly subtotal between months, a total over a named range (`=SUM(Amounts)`) — is taken out of the pattern instead of being flagged as inconsistent. Along a Total row (or down a Total column) a cell that is exactly one SUM or AVERAGE of its block is compared by the block it totals, with SUM and AVERAGE counted as one function (an amount adds up, a price or a % is averaged), so a row that sums most columns but averages the price or the margin % is not flagged. Everything else in such a formula still counts: a total that stops a row short, a hard-coded plug (`=SUM(B5:M5)+500`), a multiplier (`*1.1`) or a different function (`=MIN(…)` in a column of `=MAX(…)`) is flagged.
  - *Headers.* A formula heading a column of numbers with a text result (`="Amount ("&G1&")"`, a month label), and the first cell of a recurrence right after a header (`=D2` above `=E2+D3`, `=Inputs!B2` before `=B2*1.05`), are not inconsistent. Dates shown with digits only (`01.02.2026`, `1.2.2026`, as German and other locales display them) read as labels, like `Feb 2026`, not as numbers.
  - *Ranges.* A range is flagged only when the cells right after its end hold **plain data of the same kind** as the range: not a formula (a total, a forecast), not a text header after numbers, not a cell of a header row or of a totals row of the range's own table. A Total row of *another* table beside it (a blank column away) does not end the walk, so it cannot hide a month the range leaves out. A range is not flagged when the formula's own fill picks up where it leaves off — a formula right next to it along its column or row reads the next block or the next window of the same line (Q1 `=SUM(B5:D5)` beside Q2 `=SUM(E5:G5)`; `=AVERAGE(B2:B4)` above `=AVERAGE(B3:B5)`) — nor when it is a step of a running total: an anchored start whose end is on the formula's own row (`=SUM($B$2:B7)` in row 7), or an unanchored one (a report typed cell by cell) whose neighbouring formula cells read ranges from the same start ending one cell later and one earlier (or two later). Only the formula's own neighbours count. A moving-average column over the data reads a window starting right after almost any row, and does not excuse an unrelated total that stops short (`=SUM(B2:B12)` under a 3-month average while B13 is plain); a year-to-date column beside the data, or on another tab, reads ranges of every length from the same start and does not excuse one either; nor does a correct total elsewhere excuse a short one. Subtotals of consecutive blocks placed apart (a weekly sum every seventh row beside daily data) are not each other's neighbours, so each is reported, as before this change. The largest source of noise was a formula to the right of a range in the same row — the quarterly columns after the months — being treated as a total that should cover every cell up to itself.
  - Still flagged: a broken fill-down in the middle of a run, and `=SUM(B2:B9)` with B10 a plain number continuing the data — also when another table's Total row sits level with B10, and also when a moving average or a year-to-date column (on the same tab or another) reads the same data. And a plug, a multiplier or a different function in the middle of a Total row or column.
- **Cost follows the cells present.** Nothing the range check keeps is sized by a tab's bounding box, by the number of tables, or by how far its walks go: it keeps the cells a tab holds, listed by column and by row, and an index of the tab's totals ((number of totals) × log2 of that × 4 bytes). The neighbour checks run before any walk past a range's end, and a range with nothing after it to walk (a total right under or beside its range) builds nothing. Each column or row is read as the cells it holds, so a tall log beside a wide table, or one note in column ALL, adds no cost per row. A walk skips a run of plain data in one step — each cell is scanned at most once per kind of walk (four kinds), whatever the number of ranges or tables — and asks the totals index once for the first total of its own table in that run, measuring its table only when a line in the run holds a total; a finding keeps the count and the first 10 cells it misses. An earlier version of this change kept a scan per table instead: a daily log whose totals each sat in a different table (a staircase of markers beside it, and a forecast with a total on every row) took 2.2 s and +174 MB for 75,000 cells and ran out of memory in a 128 MB heap; it now takes 0.4–0.5 s and +65 MB (release/1.6: 0.23 s, +28 MB). One cost is not linear in the cells: a table is measured once per distinct span of range that walks into a line holding a total, reading the table's lines each time (840 spans along the rows of a 5,000 × 60 table: 0.7 s in all, release/1.6 0.37 s). `tests/sheets-analysis.test.ts` audits tabs of 8,000 to 50,000 rows: a 7-day moving average, a running total, weekly subtotals (also beside a forecast table with a total on every row), a 20,000-row log beside a 365-column block, 8,000 row totals with one note in column 3000, a table whose Total column was pasted as values, and the staircase at 30,000 rows. It holds each under 2 s, +96 MB of heap (read after a full GC) and +16 MB of ArrayBuffers (a Worker isolate has 128 MB, and typed-array memory does not show in heapUsed); each takes 0.03–0.5 s here, release/1.6 under 0.3 s. The check still does more than release/1.6's, which looked at one cell past each range: on the largest tabs measured it takes up to twice the time and 2.3 times the heap growth.
- **Formulas with many references cost each range a lookup, and what the check keeps is bounded.** The neighbour checks above (`deliberateEnd`, `expandingFamily`) used to walk every reference of each formula next to a range again for every range — up to 16 walks over the 4 neighbours and two steps away, each building a new list — so a formula's cost grew with the square of its ranges, and every formula cell's resolved references (one object each, over 100 times the size of its text) were kept until the audit returned. Now a formula's ranges are kept as numbers — only bounded ranges of two or more cells, the only references a total or a short range can be, each once — with its column and row ranges indexed by line and start, so each neighbour check is a binary search. They are memoised by formula text while the formula's tab is checked, in a memo of two generations bounded in estimated bytes (`MEMO_BYTES`, 24 MB of estimated bytes each, counting the formula text it is keyed by): a relative fill-down has a different text in every row, and an unbounded memo kept every one of them for the whole tab. The walks past a range's end are memoised per tab, only those that got past the end, up to 4,096 at a time; the R1C1 shapes the fill-down check compares are kept once per distinct shape, up to a bounded weight. Everything is released when that tab's checks finish. Measured on the fixtures in `tests/sheets-analysis.test.ts` (time, heap growth read right after the audit): 3,000 rows × 4 scenario columns of a 40-range SUM 4.8 s and +119 MB before the lookup, 0.9 s and about +10 MB now; 40 cells of a 49,000-character sum of 4,083 two-cell ranges 12.9 s → 0.3 s; 40 cells of a 49,000-character `=A1+A1+…` (16,333 references each) 0.4 s and about +22 MB now, and node finishes it in a 17 MB heap. The test holds these under the same 2 s / +96 MB / +16 MB bounds as the cases above, and the dense one under +48 MB. A second test audits four more fixtures in a child node capped at a Worker's 128 MB of heap. The smallest heap (`--max-old-space-size`) each finishes in, bisected twice as the least in which two runs in a row finish, for the audit before this change → an earlier version of this change, which kept every formula cell's resolved references and every walk result for the whole audit → now: 20,000 isolated 40-range SUMs 34–36 → 294 → 44 MB; a relative fill-down of that SUM, 20,000 rows × 2 columns, 74 → 398–412 → 78–80 MB; 300 isolated 49,000-character sums of about 4,000 ranges no other formula reads 26 → 420 → 36 MB; 300 such sums down one column 60 → 298–306 → 58–60 MB. Each ran out of memory at 128 MB in that earlier version. A single run's need varies by several MB: before this change, the fill-down finished in a 62 MB heap once in three tries and failed every time at 60 MB. With the formula, walk and shape memos of this change left unbounded, the four need 96, 150, 82–86 and 156–158 MB. The error cells come from the same `gridErrors` the post-check of `sheets_delete_sheet` and `sheets_batch_update_spreadsheet` reports, so the two cannot disagree; the list is unchanged, field for field.
- **Whitespace costs time in proportion to its length.** Two regular expressions tried every split of a run of whitespace between parts that both take it. The test for "a SUM or AVERAGE and nothing more" (a totals row's shape) cost the cube of the length of a run of spaces after its "(", on every cell of a fill-down: three cells of `=SUM(<2,000 spaces>(B1))` took 3.3 s, and 49,000 spaces would take hours. It is now parsed step by step. The test for "this displayed value reads as a number" cost the square of a run of spaces, on every value a walk or a header check reads: five text cells of "1", 49,000 spaces and a letter took 11.7 s to audit. Runs of whitespace are now collapsed to one space first, which accepts exactly the same values, and a value over 1,000 characters is not a number. `tests/sheets-analysis.test.ts` audits both with 49,000 spaces under the 2 s bound.
- **Output fields.** `errors` is the list of error cells, as before; the counts are the new `errorCount` and `warningCount` beside `ok`. `differsFrom` is an object keyed by direction (`{ "column": "C2 =B2*2" }`) and replaces the `direction` field. `dataBeyondRange` is an object keyed by range (`{ "Data!B2:B4": ["B5"] }`) and replaces the `range` field. It lists at most 10 of a formula's short ranges, the 10 fewest cells short, in formula order; when there are more, `shortRanges` counts them all, and `missedCells` always totals the cells all of them miss. `missingSheets` names at most 10 sheets, in formula order, with `missingSheetCount` when a formula names more (it used to list every one). Both lists were held whole for every such cell before `max_findings` applied. 150 cells of a 49,000-character formula of about 7,000 two-cell ranges over a block of numbers ran out of memory in a 128 MB heap, and in a larger heap the summary was 4,133,786 characters; 700 cells of a 49,000-character formula naming about 6,000 missing sheets ran out of memory too, and their summary (200 errors and 200 missing-sheet findings at `max_findings` 200) was 8,982,690. `tests/sheets-analysis.test.ts` audits both in a child node capped at 128 MB: summaries of 5,310 and 109,590 characters now. `summary` keeps its five counts. `formulas` now counts each cell once when `ranges` overlap, as `cellsScanned` already did.
- On the test model (a monthly budget with totals and quarters, a line-item table, a plan with a moving average and forecast rows, two blocks with headers, one short total): 66 warnings before, 2 of them real; now exactly those 2, in a 520-character reply instead of 8,524.
- Grid loading, `sheets_trace_precedents` and `sheets_trace_dependents` are unchanged. `tools/list` grows by 202 bytes on the full surface (160,807 → 161,009 on `release/1.6` with the Sheets batch-update change; the `detail` parameter and a rewritten description); the audit is not on the compact surface. Model-facing bytes: `group:sheets` 21,781 → 21,983 (ceiling 22,000), full 137,595 → 137,797 (140,000), the gmail+calendar+drive+docs+sheets profile 70,492 → 70,694 (71,000); no ceiling in `tests/budget.test.ts` is raised.

### `sheets_batch_update_spreadsheet`: short replies, values and structure in one call, deletion previews that show what breaks; snapshots and a post-check on the other destructive Sheets tools

A QA session on the JEV build found this tool's replies long and repetitive (49 formatting requests came back as 11.7K characters), a formatting-only paste flagged as an overwrite, no way to write values and change structure in one guaranteed order, a deletion dry run that said "contents are lost" without showing them or the formulas that would break, and no check after structural changes. Same tool name and annotations; three new optional parameters (`reply`, `post_check`, `snapshot`) plus a `writeValues` request type inside `requests`; the default reply of a real run is now the short one. `sheets_delete_sheet` and `sheets_clear_range` gain the same opt-in snapshot, and `sheets_delete_sheet` a post-check (both below); every grid read these features take, the re-read `verify` makes after a batch and a dry run's read of the cells a request overwrites are bounded in grid cells and in response bytes, and the grid reads ask only for the cell fields they use; the formula references those reads hold are resolved in batches bounded by formula characters, and the values a batch's `writeValues` may hold are capped (see **Resource bounds**).

- **`reply`: `"summary"` (new default) or `"full"`.** A real run returns `applied`, `totals`, warnings grouped by text (`{warning, requests: [indexes], types}`) and `changes` only for requests that carry a warning or a non-empty Google reply, without repeating the warning inside each entry (20 shown, then `changesOmitted`). 49 identical formatting requests now answer in 46 characters of JSON; `reply="full"` is the previous shape, unchanged (9,616 characters for the same batch). Dry runs still list every request — the plan is the point of a dry run — and use the grouped warnings.
- **copyPaste warnings follow Google's paste types.** `PASTE_FORMAT` (format + data validation), `PASTE_DATA_VALIDATION` and `PASTE_CONDITIONAL_FORMATTING` change no values: no "destination overwritten" warning, the effect says what is replaced, and the totals count `cellsFormatted`. `PASTE_NORMAL`, `PASTE_VALUES`, `PASTE_FORMULA` and `PASTE_NO_BORDERS` (normal minus borders, so it pastes values) keep the warning, now count `cellsWritten` and are re-read by `verify`. The range reported is the block Google actually pastes into (the whole source from the destination's top-left, turned sideways when `pasteOrientation` is `TRANSPOSE`, repeated when the destination is a whole multiple of it), so a dry run previews those cells.
- **Every value write is recognised as one.** `pasteData` is described as overwriting values, over the block its text covers (as many rows as lines, as many columns as the widest line; the anchor cell for an HTML paste), and a `repeatCell` whose field mask is `*` counts as a value write even when its cell carries only a format, because that mask clears every value in the range. Before, neither carried a warning, so `snapshot=true` took no backup of the tab they overwrote, `verify` did not re-read them and the summary reply did not list them.
- **`{writeValues: {range, values}}` inside `requests`.** Google applies a batchUpdate in order and all-or-nothing, but writing values and deleting rows used to take two calls with nothing ordering them. Each writeValues is translated server-side into `updateCells` (fields `userEnteredValue`, formatting kept) at the position it was given. `range` is an A1 block with its tab and must be exactly the array's size, so a block one column off is an error that names the block that fits, not a shifted write. `{writeValues: {sheetId, range: "A1:C2", values}}` is accepted too, so a values-plus-structure batch does not repeat a long (quoted, often Hebrew) tab name in every range: a range that also names a tab must name that one, and an unknown or non-integer `sheetId` is rejected with the tab list; a range without a tab and without `sheetId` is still rejected. Numbers stay numbers, booleans booleans, strings starting with `=` become formulas and other strings are stored as typed text (no number or date parsing, unlike `USER_ENTERED`); `''` clears the value and `null` leaves the cell untouched, as in `sheets_write_range` (a row holding a null becomes one `updateCells` per run of values, while consecutive rows without one stay in a single `updateCells`, all in order). An unknown tab, a range without a tab, an unbounded range or a non-scalar cell fails before anything is read or written. So does a batch whose writeValues together hold more than `WRITE_VALUES_MAX_CELLS` = 100,000 values that are not null, or become more than `WRITE_VALUES_MAX_UPDATES` = 10,000 updateCells (one per writeValues, more where nulls split a row into runs): the updateCells body is built in memory, a CellData pair per value and an updateCells object per run, so uncapped 1,000 × 500 values with alternating nulls and 120,000 × 5 dense values ran out of a 128 MB heap (measured under Node with the tool's own code and `verify=false`), and 200,000 × 1 peaked at about 107 MB. The error points at `sheets_write_range` and `sheets_batch_write_ranges`, which send the values as given, for large blocks; a dry run is refused the same way. At the caps, 100,000 one-value rows peak about 32 MB above the caller's own values, 10,000 one-cell runs about 10 MB and 10,000 one-cell writeValues about 25 MB (their per-request bookkeeping included). It is described as a value write ("overwrites values"), previewed in dry runs (charged its whole block, nulls included, see **Resource bounds**) and re-read by `verify`. A block's width is taken with a loop: an argument spread threw "Maximum call stack size exceeded" past about 120,000 rows, which a block of mostly nulls can have within the caps.
- **Deletion previews** (dry run) for `deleteDimension`, `deleteRange` and `deleteSheet`: the populated cells about to be lost (formulas as `=…`, 50 rows × 26 columns from the first populated row and column in the span, so leading blank rows do not fill the window, with `cellsWithData` and `rowsOmitted`/`columnsOmitted`) and every formula outside the deleted span that reads into it — `becomes: "#REF!"` when a reference lies entirely inside the span, `"loses the deleted cells"` when it only overlaps it — with `dependentFormulas`/`refErrors` counts, #REF! first, 25 listed. References are resolved by the same code as `sheets_trace_dependents`, so named ranges (including one on the first tab, which Google returns without `sheetId`) and references from other tabs count. It costs two grid reads, bounded as described under **Resource bounds** below: the deleted cells themselves (clipped to the tab's grid) with only each cell's formula or displayed value — a shown value is cut at 160 characters, like a listed formula — and then the formulas of every tab while they fit, otherwise the deleted tabs first and then the others in tab order, each while it fits. A preview names the tabs whose formulas were not checked, and a deletion on a tab that did not fit gets a note instead of a preview; when only the deleted cells could not be read (over a budget, or the read failed) the preview says `contents not shown` in its `note` and still lists the formulas that break. The first 20 deletions of a batch are previewed; the rest say so. If the formulas read fails, the dry run still returns the plan, with `preview: {note: "preview unavailable: …"}` on each deletion. A preview taken after an earlier request in the same batch reshapes the tab carries a `caveat`: it shows today's cells at those coordinates. Because these previews (and the existing overwrite previews) quote the spreadsheet's own cells and formulas, a dry run that shows any starts with the `provenance` notice every Sheets read carries; so does a real run whose `postCheck` lists formulas.
- **`post_check` (default true).** After a real run containing `insertDimension`, `deleteDimension`, `moveDimension`, `insertRange`, `deleteRange`, `cutPaste`, `sortRange`, `randomizeRange`, `deleteDuplicates` or `deleteSheet`, the tool re-reads the tabs with the audit's own grid loader (each cell's formula and error only) and reports `postCheck: {sheets, errorCount, ok, errors: [{cell, error, formula, message}]}`: `errorCount` is the number of error cells, `errors` lists the first 20 and `errorsOmitted` counts the rest (`errorCount` is also the name `sheets_fill_range`'s verification gives its count). It reads every remaining tab, not only the changed one, because deleting rows on one tab breaks formulas on another — within the same bound as the preview: the changed tabs first, then the others, each while it fits; every tab left out is listed under `postCheck.skipped` with a `note`, never read in part, and when nothing could be read there is no `ok`/`errorCount` at all. It is a state check, not a diff: errors that predate the change are reported too, and a `postCheck` with errors says so in its `note`. The tab list and grid sizes are re-read after the batch (one small metadata read), so a tab the batch renames is read by its new title, a tab it adds or grows counts against the bound at its new size, and snapshot backups are left out. Every read that names tabs names them quoted (`'Q1'`): Google reads an unquoted `Q1` or `Jan2024` as that cell of the first sheet, and a name shared with a named range as the named range, so a tab titled like a quarter or a month would be checked as one cell and come back clean.
- **`snapshot` (default false).** When set, each existing tab touched by a request that can lose data (deletions, cutPaste, value writes and other overwrites such as merges and find/replace) is first duplicated, in a separate batchUpdate, as a hidden tab titled `<title> (backup YYYY-MM-DD HH:MM UTC)` — unique and within Google's 100-character tab title limit — and reported as `snapshot: [{sheet, backupSheetId, backupTitle}]`. It is off by default so the tool never adds tabs to someone's file unasked; a destructive dry run says `snapshot=true` would keep a copy. Backups are ordinary hidden tabs (their formulas that read other tabs still recalculate) and stay until someone deletes them. If Google rejects the main batch with a 4xx, nothing was applied and the backups are removed again; after a timeout or a 5xx the outcome is unknown and they stay, and the error then names each hidden backup tab (title and sheetId), as it also does when removing them after a 4xx fails. `sheets_delete_sheet` and `sheets_clear_range` take this snapshot through the same code.
- **Nothing after the write turns a success into an error.** Once the batch is applied, a failed verification or post-check read is reported in the reply rather than thrown: a thrown error reads as "nothing happened" and invites a retry that deletes the rows twice. `verify` re-reads the cells every value write lands on — `writeValues`; `updateCells` and `repeatCell` whose field mask covers values; `pasteData` of delimited text, over the block its lines cover; a `copyPaste` that pastes values, over the block Google pastes into; a `cutPaste` that pastes values, over its source's block at the destination; and `autoFill`, over its `range` or the rows (columns) `fillLength` adds to its source — under its tab's title after the batch, unless a later request in the same batch really moves or deletes its cells: `insertDimension` / `deleteDimension` at or above its last row (left of its last column), a `moveDimension` span across it, `insertRange` / `deleteRange` shifting through its columns (rows) from at or above its end, a `cutPaste` source, `sortRange`, `randomizeRange` or `deleteDuplicates` range intersecting it, `deleteSheet` of its tab, or a grid shrunk below it. A delete further down the tab leaves the block where it is, so it is re-read. A moved block is not re-read at stale coordinates; the `note` names it and the request that moves it, and says `postCheck re-read their tab(s)` only when the post-check actually read those tabs. Every value write that is not re-read is named in the `note` with the reason: moved by a later request, over a budget (below), on a tab the same batch adds (not read, so the read cannot fail), covering no cell of its tab's grid after the batch, sized by a tab's grid when the tab sizes after the batch could not be read (named by request index, with the error), or a write whose cells are not known before it runs — `findReplace`, `textToColumns`, a `pasteData` of HTML and an `autoFill` past its source's open end, listed by request index, with `postCheck re-read their tab(s)` when the post-check read them. Before, a write over a whole tab (a range that is only `{sheetId}`), a value paste (`copyPaste`, `cutPaste`, `autoFill`) and a write on an added tab were neither re-read nor mentioned, although `totals` counted the `copyPaste` as written, and a range that left out only an end bound (rows 5 to the end) was re-read as its first row or column. The re-read is one grid read, bounded like the others (see **Resource bounds**): each written block is charged against the same 100,000-cell budget at every cell the read covers — the whole block, not only the values written into it, so a writeValues block's nulls count too — and a write with an open end — a whole row, column or tab, or a GridRange that leaves out an end bound — is re-read as the closed block the tab's grid holds after the batch and charged that (a GridRange without `sheetId` is on sheet 0, as in the API), as is a value paste whose source or destination leaves out an end bound (a pasted whole column is as long as the grid); the response is capped at 8 MB; and each cell is asked for its effective value only. The grid sizes come from one small metadata read after the batch, made only when the batch holds such a write and shared with the post-check, so the rows or columns an earlier request in the same batch appends or inserts are re-read with the write, and a read never runs past rows an earlier request deletes. Sized on the grid from before the batch, a whole-column write after an `insertDimension` of 500 rows left those 500 rows unread without a word, and a write into rows an `appendDimension` had just added came to 0 cells and was dropped, so its errors came back as a clean reply. A written range beyond the cell budget, or a re-read refused over the byte cap, is named in the `note` and not read. A block of more than 5,000 cells is no longer left out without a word, as it was before: it is re-read when it fits the budget. Deciding which blocks a later request moves is linear in the batch and runs only with `verify` (see *CPU* under **Resource bounds**).
- **`sheets_delete_sheet`: `snapshot` (default false) and `post_check` (default true).** `snapshot=true` first copies the tab to a hidden backup tab — the same naming, uniqueness and 100-character rules, the same `snapshot: [{sheet, backupSheetId, backupTitle}]` reply, and the same cleanup when Google rejects the delete (a 4xx: the backup is removed again; a timeout: it stays and the error names it). `post_check` finds, before the delete, which other tabs hold a formula that reads the tab (references and named ranges resolved as in the deletion preview) — afterwards their formulas no longer name it — and re-reads only those tabs after it, reporting `postCheck` in the batch tool's shape (`errors` = list, `errorCount` = count, `note`, `skipped`) with the provenance notice first when it quotes formulas. A tab no formula reads needs no second read (`postCheck: {errorCount: 0, ok: true, note}`). Its reads keep to the same bound; a failed read is reported, never thrown, and never blocks the delete. The reply now also names the deleted tab (`sheet`). With `post_check=false` and no snapshot the tool makes exactly the one call it always made, with the same reply; an unknown `sheet_id` otherwise fails before anything is deleted, naming the tabs. Flags and annotations are unchanged (write, destructive, idempotent).
- **`sheets_clear_range`: `snapshot` (default false).** `snapshot=true` first copies the range's tab to a hidden backup tab, the same way, and adds `snapshot` to Google's reply. The tab comes from the range (`'Tab'!A1:B2`, a whole tab, or a named range); a range that names no tab is rejected rather than guessed, since Google would clear the first visible tab. Default calls are unchanged, as are the flags and annotations.
- **Resource bounds.** Every includeGridData read these features take — the deletion preview, the batch post-check, `sheets_delete_sheet`'s check and the batch's `verify` re-read — is bounded three ways. *Cells:* at most `GRID_READ_MAX_CELLS` = 100,000 grid cells per read (rows × columns from the tab metadata, an upper bound on what Google can return; for the verify re-read, rows × columns of each written block, an open end cut at the tab's grid after the batch), down from 1,000,000; the tabs left out are named, never read in part, and so are the written ranges. *Fields:* a check read asks only for each cell's formula and error (`userEnteredValue/formulaValue,effectiveValue/errorValue`), so the text a tab holds is never downloaded, and the preview's read of the deleted cells only for the formula or displayed value. The verify re-read asks only for each cell's effective value, which says both whether the cell holds a value and whether it is an error; it asked for the formatted value too, so a text cell's text came back twice. That read is `verifyCells`, shared with `sheets_write_range`, `sheets_batch_write_ranges`, `sheets_append_rows` and `sheets_fill_range`, so their re-reads drop the formatted value as well, with the same replies; they pass no byte cap. Asking for every field returned each text cell three times: a 1,000-row tab of 5,000-character log entries (28,600 grid cells with its neighbour, under the cells cap) made a 90M-character post-check response, which exhausted a 128 MB heap after the batch had been applied. *Bytes:* `GoogleClient` gains a `maxBytes` request option, and these reads accept at most `GRID_READ_MAX_BYTES` = 8 MB (sent with `prettyPrint=false`), counted while the body streams; a larger response is refused without being buffered or parsed, its tabs are listed under `postCheck.skipped` ("over the 100000-cell or 8 MB read budget"), the preview says it is unavailable, or the verify `note` names the written ranges it did not re-read, and the change itself is still made and reported. *Previews:* a dry run's read of the cells a request overwrites (values:batchGet, shown up to 200 cells per range) is charged the grid cells of the block it reads — rows × columns of the range, an open end cut at the tab's grid — not the request's `cells`, which for a `writeValues` counts only the values that are not null and for an `updateCells` with a `range` only the cells in its `rows`; a range over 200 such cells gets a `note` with its size instead of a read, and the ranges read keep to the same 100,000-cell budget together (a preview past it says `preview skipped`). That one read is capped at 8 MB (sent with `prettyPrint=false`); refused over it, each of its previews says `preview unavailable` and the dry run still returns the plan. Before, a writeValues with 200 values over a 1,000-row, 26-column block of long text was read in full, and so was an `updateCells` over a large `range` with one cell in `rows`. Measured with the tools' own code under Node, against a fetch that streams Google-shaped JSON: the post-check, dry run and `sheets_delete_sheet` calls that ran out of memory at 128 MB on those text tabs now peak at 15–25 MB of heap. *Formula references:* keeping a read under both caps does not by itself bound the work done on it. Every reference resolves to an object that takes over 100 times its text in heap, and references were resolved 1,000 formula cells at a time, so one batch could hold all the formula text a read allows: 1,000 cells of 8,000-character formulas (889 references to the tab being deleted in each, 7.7 MB) and 40 cells of 49,000-character formulas (16,333 references each, a 1.9 MB read) ran `sheets_delete_sheet` on its default path out of a 128 MB heap before the delete was sent, and the first also a dry run of a `deleteSheet`. They are now resolved in batches of at most 1,000 cells and `RESOLVE_CHUNK_CHARS` = 100,000 characters of formula text (a longer formula alone), so a batch of formulas within Google's 50,000-character cell limit resolves at most a few tens of thousands of references. Measured under Node against a fake that answers from serialized JSON: those three calls now complete within a 128 MB heap, peaking between about 20 and 65 MB (garbage included, varying from run to run), and the two `sheets_delete_sheet` calls also complete with a 40 MB old space; `sheets_delete_sheet` over 100,000 short formula cells with 3,000 named ranges (two 6.1 MB reads), whose batches were already under the character bound, peaks between about 55 and 90 MB and needs more than a 64 MB old space, within a 128 MB heap. *CPU* stays linear in what is read: named ranges are looked up in a map built once per spreadsheet, not a list copied and scanned per formula (a dry run over 75,000 formulas with 3,000 named ranges took 9.3 s, now about 0.4 s); a sheet name in a formula reference is matched up to Google's 100-character tab title limit, not to the end of whatever run of name characters or apostrophes follows (twenty 50,000-character formulas took 25.7 s, now about 0.25 s); references are resolved in batches of at most 1,000 formula cells and 100,000 characters (above) and scanned once for every previewed deletion together, keeping only counts and the listed dependents (at most 20 deletions previewed). The batch tool's own bookkeeping is linear in the number of requests, which nothing bounds (a script can send tens of thousands): the requests that can move cells are indexed once per tab, so a written block is tested only against the later ones on its own tab, and all those tests together stop at `MOVER_CHECKS_MAX` = 1,000,000 (about 50 ms) — blocks past it are named in the `note` and not re-read; with `verify=false` none of it runs. Its heap is linear in the requests too, about 1 KB per request of any type (30,000 one-cell `updateCells` peak about 43 MB under Node, the parsed requests included), and nothing but the transport bounds how many a call sends. ### `sheets_fill_range`: write a formula once, fill it across a range; `sheet_id` on the value writes

**Why.** In a QA session on the Sheets tools, writes were the heaviest calls: about 8.6K characters each, about 21.6K once the Hebrew was escaped into JSON. Most of that was one formula written out twelve times, once per month, every copy repeating a long Hebrew tab name, with its references shifted by hand. Spreadsheet users do this with the fill handle; this server had no equivalent.

- **New write tool `sheets_fill_range`.** It puts one formula or value into the top-left cell of a range and fills it over the rest. Relative references adjust exactly as they do when you drag the fill handle. The formula is sent once. For the shape QA hit (twelve months, a long Hebrew tab name in the formula), the request drops from 4,595 to 424 characters with non-ASCII escaped, about 91% less. `tests/sheets-fill.test.ts` reproduces that case.
- **How it writes.** One `spreadsheets.batchUpdate` with two requests, in this order: `updateCells` on the top-left cell, then `copyPaste` from that cell onto the whole range with `PASTE_NORMAL`. Google adjusts relative references on a copyPaste. `repeatCell` does not: it would write the identical formula text into every cell, so it is never used. As with the fill handle, the top-left cell's format is copied too. The value is typed by content, as if typed into the cell: `=` starts a formula, a plain number is a number, TRUE/FALSE is a boolean, a leading apostrophe forces text, and anything else is text. Dates and percentages stay text; write them as a formula. `value` is capped at 50,000 characters, what one cell holds. Before the third verifier round it had no cap, and the number pattern backtracked quadratically on a long run of digits that is not a number: a value of 80,000 digits and an `x` cost about 3 seconds of CPU, 160,000 about 13. The pattern accepts the same numbers and is now linear (`tests/sheets-fill.test.ts` types 160,000 digits and an `x` inside a 250 ms budget).
- **`sheet_id` instead of a tab name.** Give the numeric tab id with an unqualified range (`C2:N2`) and the tab name is never sent at all. The reply names the tab once. If the range names a tab and `sheet_id` names a different one, the call is refused. An unqualified range with no `sheet_id` is accepted only when the spreadsheet has one tab. A fill can overwrite thousands of cells, and "the first tab" would be a guess.
- **`sheet_id` on `sheets_write_range` and `sheets_batch_write_ranges` too.** QA asked for short aliases for tab names, so a long Hebrew tab name is not repeated in every range. Both value writes now take the same optional numeric `sheet_id` as the fill tool: on `sheets_write_range` beside `range`, and on `sheets_batch_write_ranges` in each `data` entry, next to the range it qualifies, so one call can write to several tabs. An unqualified range is sent with the tab's title, quoted as A1 needs it (`'תקציב 2026'!C2:N2`, `'Bob''s plan'!B2`). A range that names its tab is sent as given if the tab is `sheet_id`'s. There is one implementation: `qualifyRange` uses the fill's tab resolution, so an unknown `sheet_id`, or a tab name that is not `sheet_id`'s, fails with the fill's exact error text. `sheets_batch_write_ranges` prefixes the entry (`data[1]: …`). Nothing is written when any entry fails. Metadata is read once per call, and only when a `sheet_id` is given. Without `sheet_id` nothing changes: no extra read, and the range goes to Google exactly as given, so an unqualified range still lands on the first tab. The fill tool's one-tab rule stays specific to the fill.
- **Refused before anything is written, with an error that says what to do:** a range that is not a closed block of cells (`C:C`, `C2:C`, `C2:N2:Z9`, a bare tab name, a named range); a range that names row 0 (`A0:A5`); an unknown tab (the error lists the tabs and their ids); a range past the tab's grid; more than 50,000 cells.
- **Verified like the other Sheets writes.** With `verify` (default true), the filled range is re-read and any cell that evaluates to an error is reported with Google's message. Above 5,000 cells only a band at each end is re-read. A wrong formula shows at the top-left, and a reference that runs off the data breaks at the far end. The bands are listed under `verifiedRanges`, so `ok` is never read as "every cell checked". The reply stays small when the fill goes wrong: one formula fills every cell, so one mistake, such as a misspelt tab name, breaks every cell it reaches. The reply lists the first 10 error cells, gives the total as `errorCount`, and sets `errorsTruncated` when there were more. The `warning` counts all of them and names five. Listing every cell made a 2,000-row fill with a misspelt tab name reply with about 230,000 characters. A 5,000-row one passed the server's output cap, was cut off, and was no longer valid JSON.
- **Flags and naming.** New verb `fill` in the name grammar, kind `mutating_idempotent`. The annotations match `sheets_write_range`: destructive, because it overwrites, and idempotent, because refilling the same value changes nothing. Like every write, it is not registered on a read-only deployment.
- **Pointers.** `sheets_write_range` and `sheets_batch_write_ranges` now end with "Same formula in many cells: sheets_fill_range." The fill tool is not one of the compact surface's recipe tools. With `TOOL_SURFACE=compact` it can still be called by name, but its schema is not listed. A compact deployment that wants the model to see its inputs adds it with `TOOL_SURFACE_ADD=sheets_fill_range`.
- **Routing.** A manifest route block, `fill` in the EN/HE routing lexicon, and mutation-gate cues let "fill the formula down column C", "copy this formula across to December", "copy the formula in C2 to D2:N2", "fill C2:C40 with =B2*1.17" and `תעתיק את הנוסחה לכל החודשים` reach the tool.
  - **Only on evidence of a fill.** The mutation gate offers `sheets_fill_range` only when the request itself asks for a fill: a direction ("fill down", "across", "right") or, for "copy the formula", a destination (see Cue shape), a formula (the word, or one typed out, like `=B2*1.17`), a drag, or autofill. A generic write verb such as "write", "update" or "set" does not bring it in, although it does bring in the other tools of its kind. Evidence decides in the other direction too: with it, the fill tool is in the gate however it ranks. The fill tool is added on top of the gate's five ranked writes and is never traded for one of them. The gate also ranks the other writes without it, so it takes none of the router's ten places the other writes are drawn from.   - **Only where the request could mean Sheets.** "Drag down", "drag across" and "autofill" name no product.   - **Phrase reading.** Every other gate cue matches when the request holds all of its words, anywhere and in any order, and Hebrew clitics are folded away first. A fill term (`VERB_LEXICON.fill` and the gate's fill cues) is now read as a phrase: its first word is the verb, and every later word is after it in the verb's own clause, in any order ("fill the tool costs down", "copy down the formula", "fill the total in the last column down to the bottom of the sheet"). The clause ends at punctuation followed by a space (the `:` of a range and a decimal point are inside a word), at "and", "or", "but" or "then" (in Hebrew או, אבל, אז, ואז), or at a Hebrew word that joins "and" to a verb (ותגלול, ותשלח). So "fill the names in column C and scroll down" reads no fill. "The right" before a noun is the adjective ("fill the names in the right column"), unless "to" or "toward(s)" comes first ("fill it to the right"). "Fill in" and "fill out", also with a pronoun between ("fill it in"), are not the fill verb. "Right now", "right away", "right after", "right before", "right here", "right there", "right below" and "right above" are not a direction. ### Sheets reads keyed by cell address

**Why.** A QA session on the JEV build wrote a note into column C that belonged in column D, and only noticed on a re-read. The Sheets reads return positional rows: Google drops each row's trailing empty cells, and index 0 is whatever column the range starts at, so finding "the cell under the Note header" meant counting positions — and the count was off by one. The fix is to stop making the model count.

- **`shape: "grid" | "cells"`** on `sheets_read_range`, `sheets_batch_read_ranges` and `sheets_read_cells`. `grid` is the default and is the existing output, byte for byte (pinned in `tests/sheets-read-cells.test.ts` against what these tools returned before). `cells` returns an object keyed by unqualified A1 address holding only the non-empty cells — `{"D7": {"value": "90", "formula": "=B7-10"}}`, with `formula` only when `include_formulas=true` and only on cells that have one — plus the range Google echoed, `rowCount`/`columnCount` of that range and `cellCount`. A blank cell is simply absent, so "is D3 empty?" is a lookup rather than arithmetic. `sheets_batch_read_ranges` returns one such entry per range, in the order asked.
- **`sheets_read_cells` gets addresses too.** Its grid gives one origin (`startRow`/`startColumn`) and positional rows that Google also cuts short after the last non-empty cell, so finding a cell there meant the same `startColumn + index` counting. With `shape=cells` its compact cells (`{v, f, n, note, link, …}`) are keyed by address, computed from the origin Google returns with the grid data, with `sheet` and `cellCount` alongside.
- **Addresses come from the range Google echoes, not the one requested.** A named range or a bare tab name comes back resolved (`'Tab'!A1:Z1000`), so it is addressed correctly. Covered by tests: quoted tab names with spaces, apostrophes and Hebrew; ranges that start off A1 (`C5:F9`); whole columns (`A:D`) and whole rows (`2:5`); single cells; `major_dimension=COLUMNS`; ragged rows; multi-letter columns (AA, AZ, ZZ, AAA). If the echoed range carries no coordinates at all, the call fails and says to use `shape=grid` instead of assuming A1 — a guessed origin would reproduce the very error this exists to prevent.
- **`cellCount` is always present.** `strip()` removes an empty `cells` object from every reply, so an all-blank range reads `cellCount: 0` rather than a missing field.
- **A whole-tab read builds only what one reply can carry.** An independent verifier found that `shape=cells` built one object per non-empty cell of the whole range (about 119 bytes retained each, against about 20 for the grid), that `strip()` then copied every one of them and that `JSON.stringify` ran over the result, even though `ok()` keeps only the first `MAX_OUTPUT_CHARS` (350,000 characters, roughly 17k cells). On a 17,500 × 20 tab, 350k cells ran a 128 MB isolate out of memory where the grid shape did not. Cells are now added in read order only while they fit the reply; the rest are only counted. The charge per cell is exactly what it adds to the JSON (`entryChars`, pinned by a test), and the provenance, the echoed range or `sheet` and the counts come off the limit first. A cut reply keeps `cellCount` as the total and adds `truncated: true`, `returnedCells` and a `note` (placed before `cells`) saying to read a narrower range. The kept cells are always a prefix, so the last address shows where to continue. `sheets_batch_read_ranges` shares one budget across its ranges: a range after the cut still reports its `cellCount`, with `returnedCells: 0`, and a top-level `note` appears when any range was cut. Every range's entry (its echoed range and counts) is reserved before any range's cells are built, so a first range that fills the reply cannot crowd out the entries after it; independent verifiers found that charging each entry only when its range was reached let as few as 8 ranges after a cut overrun the limit, so `ok()` cut the reply mid-string and dropped the later ranges' counts, and tests now cover 24 ranges after a full first range and 100 ranges (the schema maximum) on long quoted Hebrew tab names. A cut `shape=cells` reply is therefore still whole JSON, never cut mid-string by `ok()`. Measured with the real bundled handlers and `ok()` under `node --max-old-space-size=128`: `sheets_read_range` at 350k and 400k cells went from out of memory to a peak of about 60 MB in about 70 ms (the grid shape: about 58 MB), and `sheets_read_cells` at 300k cells went from out of memory to a peak of 117 MB. Its grid shape sits right at the limit there: 137 MB in one run, out of memory in another. The `grid` shape is unchanged.
- The provenance envelope still comes first, naming the addressed fields (`cells.*.value`, `cells.*.formula`; `cells.*.v` etc. on `sheets_read_cells`). A cell whose formula displays as blank keeps its `formula` and has no `value`.
- The descriptions of `sheets_read_range` and `sheets_batch_read_ranges` both say when to use it: before writing into a specific cell, or whenever trailing blanks matter. The routing manifest's `returns` for the three tools mention the addressed shape. `npm run jev:bench` still passes its gates with the same recall (mutation recall 100%, no forbidden selections, 98.8% overall); the larger schemas move its schema-token rows from 34,468 to 34,590 for the whole catalog (+122) and from 2,064 to 2,085 for the mean selection (+21). The committed baseline report in `bench/jev/results/baseline-deterministic/` still shows the old numbers; refresh it once, after the other Sheets changes in this release have landed.
- **Cost, measured.** `tools/list` +508 bytes on the full surface (157,799 → 158,307) and +190 on the compact one (28,334 → 28,524; only `sheets_read_range` is advertised there). Sheets group model-facing bytes 18,915 → 19,423, under the unchanged 19,500 group:sheets ceiling in `tests/budget.test.ts` with 77 to spare. `tests/sheets-read-cells.test.ts` pins this change's 508 bytes on the three read tools; whether the whole group fits is left to `tests/budget.test.ts`, which measures the real tree. No ceiling is raised: full 134,729 → 135,237 (of 140,000), five-group profile 67,626 → 68,134 (of 71,000), compact 25,630 → 25,820 (of 27,000).

### compact replies, one way to find tools, narrower access

These changes respond to a QA session run against the QA build with JEV turned on. It reported three problems: replies were pretty-printed in some cases and compact in others, even though the server instructions promise compact JSON; there were two overlapping ways to find a tool; and the server asked for full Gmail and Drive access just to edit one spreadsheet.

- **Every structured reply is now compact JSON.** Before, `ok()` indented any reply shorter than 3000 characters and left longer ones compact, so the same tool changed format depending on how much it returned. Indentation also added 25–80% more characters to typical small replies, such as an identity check, a short file list or a 10-row range, which are the replies sent most often. Now there is one format at every size. A handler that returns a plain string, such as CSV, is still passed through unchanged. Error text is unchanged.
- **One discovery rule, in `MCP_INSTRUCTIONS`:** find tools by name with the client's own tool search, and call `google_list_tools` only to see what this deployment enables. The instructions are a single static string that every deployment sends, so they do not mention `google_select_tools`, which only exists when `JEV_ENABLED="true"`. Other sentences were tightened so the text stays under the 900-character limit (now 899; it was 892).
- **`google_list_tools` also names what is switched off.** On top of the per-session counts above (`groupCount`, `toolsCallable`, `toolsListed`), it now returns `disabled` and `disabledCount` for groups this deployment does not register, which answers "why is that tool missing?" without a second call. `meta` follows `MCP_READONLY` and the JEV flag. Its description, and the description of `google_select_tools`, now say when to use each tool and point to the other, so their jobs don't overlap.
- **Narrower access is documented.** Scopes follow the enabled groups. A deployment used for spreadsheet work can set `ENABLED_TOOL_GROUPS=sheets`, and Google's consent screen then asks only for `spreadsheets`. The `sheets_power_user` profile (Sheets + Drive) adds Drive and still asks for no Gmail. Users who already connected must revoke the app at Google and reconnect, because the connector asks Google to carry earlier grants forward (`include_granted_scopes=true`). This is covered in `docs/OPERATIONS.md` ("Narrow access for one job") and the README. No scope logic changed.
- **Measured:** `tools/list` is 43 bytes larger on every surface than after the counts change below, all of it the longer `google_list_tools` description (full: 157,756 → 157,799; compact: 28,291 → 28,334). All `BUDGET` ceilings still hold without being raised. `tests/compact-replies.test.ts` covers each of the three QA failures directly.

### JEV in the QA runtime, behind a flag

**Registered and callable only where `JEV_ENABLED="true"`.** With the flag unset — every production deployment — registration and `tools/list` are byte-for-byte what they were before this change, `/health` gains no field, and the generated README tables and measurements do not move. The section below ("Still nothing is registered, listed or called") describes the state before this change and stays true of a deployment that does not set the flag.

- **`google_select_tools`** answers "which of this server's tools does *this request* need", taking the request as an argument. MCP's `tools/list` carries no user prompt, so a listing cannot be request-aware without pretending to know the task; a tool handed the request can be. It returns canonical tool names in rank order plus the evidence behind them: what the deterministic prefilter offered, what the mutation gate pinned and why, how many binary questions were put to the model, and whether the answers were usable (`fallback`). An empty result carries a `note` saying so — `strip()` drops an empty array, and a bare `toolCount: 0` reads as a bug rather than a verdict.
- **Off unless the flag is exactly `"true"`.** Unset, blank, `1`, `yes`, `TRUE` and a typo all mean off: a flag that guesses is a flag that turns itself on. The tool is appended by `toolsFor`, not folded into `TOOL_GROUPS`, so every other consumer of the catalog — README tables, measurements, the manifest/surface split — is untouched.
- **The safety argument is unchanged, not re-made.** The tool calls the same `selectTools`: the prefilter ranks READ tools only, the model may only remove from that set, and the mutation gate's tools are unioned back afterwards, unconditionally. Every failure — no key, a timeout, an SDK that will not load, an answer of the wrong type or out of range, an answer about a tool that was never asked about — lands on the deterministic selection with `fallback: true`. There is no path to an empty or ungated result.
- **`src/routing/runtime.ts`** is the one place that reads `TYPESAFE_API_KEY`. It hands it to the SDK constructor and never logs, returns, caches or embeds it, and `jevConfigured` reports only whether a non-blank value exists. The SDK is imported dynamically, so a deployment with the flag off never evaluates it and a bundling or version problem degrades to the deterministic selector instead of breaking the Worker at startup.
- `@typesafe-ai/sdk` moves from devDependencies to dependencies, because the Worker now imports it. That grows the bundle whether or not the flag is set — the byte-identity that matters here is the tool listing, not the bundle, and the claim is made that way deliberately.
- **`/health`** carries `jevEnabled` / `jevConfigured` only where the flag is set, and warns on the one state worth alerting on: enabled without a key, where every selection is deterministic while the deployment looks like it is doing more.
- **`docs/QA-JEV.md`** is the QA note: the key as a Worker secret on `google-workspace-mcp-oauth-qa` only, an exact commit deployed through `qa.yml`, and the A/B of `JEV_ENABLED` off against on with the fields to compare. It says plainly that `wrangler deploy` replaces a worker's vars, so a var set in the dashboard is wiped by the next deployment; the durable alternative is a `qa.yml` input, which is a change to `main` and not part of this change.
- **`tests/jev-runtime.test.ts`** (30 tests) pins the flag's parsing, the byte-identical flag-off listing, the narrowing a working model does, nine distinct failure modes all falling back, and that no answer or failure can drop, downgrade or invent a mutation tool. The naming and hygiene lints now read `EVERY_TOOL` — the catalog including flag-gated tools — so a tool behind a flag still obeys the name grammar and the cross-reference rules.

### JEV tool selection via TypeSafe

**Still nothing is registered, listed or called.** `tools/list` is byte-identical on every surface, the Worker bundle is unchanged, and the default benchmark run stays offline with no credentials. What lands here is the answer half of the optional middle stage `src/routing/select.ts` already had.

- **`src/routing/jev.ts`** — an `AskFn` backed by TypeSafe's System One model: one binary "is this tool required for this request?" question per deterministically prefiltered candidate, answered by a `noul` probability compared against a threshold (0.5 by default).
- **The client is injected, not imported.** The module declares the slice of `@typesafe-ai/sdk` it needs and takes an instance, so `src/` gains no runtime dependency, the Worker bundle does not grow, and every failure path is testable without a network or a key. The SDK is a devDependency used by the benchmark runner.
- **Questions are batched; decisions are not.** One request's candidates go in one `systemOne` call carrying one question each, because the API answers questions keyed by name. The contract `selectTools` sees is unchanged — one decision per candidate — and the benchmark makes 72 calls rather than roughly a thousand.
- **JEV can narrow a read set and can do nothing else.** It is only ever asked about read tools, and the gate's writing tools are unioned in after it answers, so it cannot remove, downgrade or route around the mutation gate. A write reaching the asker is answered "required" without being asked at all.
- **Anything unusable falls back to the deterministic selection**, never to an empty or a permissive one: a missing key, an auth refusal, a rate limit, a timeout, a lost connection, a missing answer, an answer of the wrong type, a probability that is not a finite number in [0, 1], and a model that declines every candidate. `selectTools` reports the fallback rather than hiding it.
- **The key is environment-only and never handled here.** `TYPESAFE_API_KEY` reaches the SDK client from the environment; `src/routing/jev.ts` never reads, stores, logs or forwards it, and the payload it builds carries the request text and public tool metadata and nothing else. The SDK's own logging is pinned off because at `debug` it logs request bodies.
- **`npm run jev:live`** runs the 72 cases against the live model, and `.github/workflows/jev-live.yml` runs it on demand with the key from a repository secret, failing loudly if that secret is empty rather than quietly measuring the deterministic selector and labelling the numbers as JEV's. Its output is gitignored and published as a workflow artifact: a live run measures one moment and is not a baseline.
- **Raw API responses are never written anywhere.** The report carries counters — calls, questions, failures, token usage, mean API time — and the selections themselves.

### tool-selection benchmark and the deterministic mutation gate

**Nothing is registered, listed or called by this change.** `tools/list` is byte-identical on every surface, and no model or network is involved: the selector is pure TypeScript over the in-process catalog, and the benchmark runs offline with no credentials.

- **`bench/jev/cases.json`** — 72 hand-written labeled requests (24 single-tool, 16 multi-step, 12 ambiguous, 20 mutation; English and Hebrew) stating which tools a correct selection must expose a schema for, and which it must never choose. `required` is a list of slots of interchangeable tools, so a label does not have to predict which of two equally good tools a selector prefers, and a two-step request that finds only its first step scores 0.5 rather than passing.
- **`bench/jev/score.mjs` + `scripts/jev-bench.mjs`** — the metrics and the runner (`npm run jev:bench`). The run is now part of CI and exits non-zero on any missed mutation tool or forbidden selection. The mutation subset is derived from the catalog's own `write` flag rather than from a case's label, so a case labeled `multi` whose last step sends an email is still held to the mutation standard.
- **`src/routing/gate.ts`** — the deterministic mutation gate. Reads "did the user ask for something to change" from the request text and the catalog alone, with no model, and computes the writing tools a selection must not lose.
- **`src/routing/select.ts`** — three-stage selection: deterministic prefilter, an optional binary question per candidate, then an unconditional union with the gate. **The prefilter ranks read tools only, so every writing tool in a selection was put there by the gate.** That is stronger than "a model cannot drop a write": the model is never offered one to drop and the ranker cannot volunteer one, so a request stating no change cannot surface a send or delete schema however the words happen to score. Any failure in the middle stage discards it and leaves the deterministic answer, reported as a fallback rather than hidden.
- **A change with no stated target is refused, not guessed at.** "Remove it" names no object, so the gate offers nothing and tells the caller to ask which was meant. A recoverable write in the same position is allowed through, and so is an irreversible one carrying its own `confirm` argument — "send it" reaches the send tools precisely because sending asks first.
- **An irreversible verb never widens to a neighbouring one.** A recoverable verb admits its whole family, so "add them to the document" can reach `docs_append_text` rather than only tools literally named `*_add_*`; `delete` never widens to `clear`, and `send` never widens to `end`.
- **Hebrew, second clause.** Hebrew joins "and" to the following word, which in a two-clause request is nearly always the verb that changes something. The shared tokenizer strips one clitic per pass and only when it recognises the stem, so `ותשתף` arrived half-reduced and `ותקבע` not reduced at all, and the gate saw no mutation in either. It now normalizes again, additively.
- **Route blocks:** `sheets_batch_update_spreadsheet` gains `rename` (renaming a tab is batchUpdate-only and the block never said so) and `drive_search_files` gains the file nouns people search by (`deck`, `file named`). Existing routing accuracy is unchanged: dev 70/72, holdout 21/25.
- **Measured, deterministic selector, no model:** required-tool recall 98.8% (81/82 slots), **mutation recall 100% (52/52 slots over 37 cases)**, 0 forbidden selections, 94% schema-token reduction, p95 selection latency 24 ms. Committed in `bench/jev/results/baseline-deterministic/`. The one miss and the known weaknesses are listed in `bench/jev/README.md`.

### v1.5 PR-6a: routing engine, tool manifest and EN/HE lexicon

**Nothing is registered, listed or described by this PR.** `tools/list` is byte-identical to PR-5 on every surface; this is library code the PR-6b discovery tools will call. No network, no model: the engine is pure TypeScript over the in-process catalog and the fixtures are hand-written.

- **`src/tools/_manifest.ts`** — `buildManifest(defs, listed)` turns tool definitions into routable entries, taking service, verb and resource from `parseToolName` (never re-parsing a name by hand) and required/optional parameters from the zod shapes. `ROUTE_BLOCKS` adds hand-written routing text for 52 core tools across all 14 groups; the other 110 route on a first-sentence fallback of their own description, so **every** tool is reachable, not only the annotated ones.

Tests fail if a verb or resource the catalog actually uses has no term in either language.

### The consent button could not be clicked: `form-action` covers the redirect too

- **`src/auth.ts` gives the consent page its own Content-Security-Policy.** `form-action` is enforced against *every* URL a form submission navigates to, including the ones it is redirected to. `POST /authorize` answers `302` to Google's authorization endpoint, so the global `form-action 'self'` blocked the submission — and Chromium reports that block against the form's action URL, which reads as if the same-origin `/authorize` had been refused and sends you looking in the wrong place. The consent page now names `'self'`, the exact origin it was served on, and `https://accounts.google.com`. Nothing else is relaxed: no wildcard, no scheme source, no scripts, no frames, and every other directive stays byte-identical to the global policy, which itself is unchanged for every other page.
- **The form's action is the request's own origin, spelled out.** It is built from `new URL(request.url).origin` and from nothing else — no `x-forwarded-host`, no configured hostname — and an origin that is not a plain `scheme://host[:port]` yields a relative action and a `'self'`-only policy rather than putting an attacker-chosen string into a header. The Google origin comes from `GOOGLE_AUTH_URL`, so the policy and the redirect can never name different hosts.
- **Every protection around the click is untouched**: the `HttpOnly; Secure; SameSite=Lax` CSRF cookie, the hidden-field/cookie equality check, the `Sec-Fetch-Site: cross-site` refusal, the client lookup, and the 10-minute KV parking of the auth request. Tests re-assert all of them alongside the new ones.
- **Proved in a browser, not only in a header.** `scripts/consent-csp-browser-check.mjs` drives a real Chromium: it renders this repository's consent page (or a deployed worker's), clicks *Continue with Google*, and fails on any CSP violation or if the browser never reaches Google's endpoint. Against the previous code it reproduces the reported console error exactly; against this change it passes. `scripts/smoke.mjs` — which every QA deployment runs — now submits the rendered form and asserts the redirect lands on Google **and** that the served policy permits both hops, so a future tightening that breaks the button fails the deployment instead of the user.

### QA checks the deployed commit with that commit's own smoke script

- **The post-deploy checks in `.github/workflows/qa.yml` were running the wrong script.** They were the last step of the `deploy` job, which checked out the branch the workflow was *dispatched* on — in practice `main` — rather than the commit it had just deployed. A QA run of a `release/*` commit therefore executed `main`'s `scripts/smoke.mjs`: any check that shipped with the deployed commit (the consent-submission assertions, most recently) never ran, and nothing in the log said so. The run passed while proving less than it appeared to.
- **A third job, `smoke`, now runs them.** It waits for `verify` and `deploy`, checks out exactly the SHA `verify` resolved (with `persist-credentials: false`), fails unless `git rev-parse HEAD` is that SHA, sets up Node 22 with the same pinned action as the rest of the file, and runs that commit's `node scripts/smoke.mjs` against the QA worker. It references no repository secret at all, its token is `contents: read`, and it installs nothing — `smoke.mjs` imports only Node built-ins, which a test now pins so a future `npm ci` there cannot become necessary unnoticed.
- **The credentialed `deploy` job no longer checks out any code.** Its checkout existed only for the smoke step; with that step moved, the job that holds the Cloudflare token runs nothing from the repository, not even the dispatching branch. It keeps `setup-node` for the pinned Wrangler install. The exact-SHA and reviewed-branch rules, the credential-free `verify` job, digest verification, the `--no-bundle` publish, per-step secrets, the TypeSafe key step and the health gate are unchanged.
- **The tests read the workflow as YAML now,** not only as text: which job runs `smoke.mjs` and from which checkout, the order of checkout → HEAD check → script, the job's `needs`/`permissions`, and that the deploy job has no checkout. They also check that every job-level `env:` reads only the contexts GitHub allows there — a `runner.*` expression in one once made GitHub reject the whole file, which shows up as a run with zero jobs and no pointer to the line. The "holds no credential" check rejects every route to one, not just `secrets.NAME`: `secrets[...]`, the whole `secrets` context, and `github.token`. The YAML parser the tests use, `yaml`, is now a declared devDependency instead of something that happened to be installed through another package.

### The QA worker runs JEV; nothing else does

- **`.github/workflows/qa.yml` turns the model-backed selection path on for `google-workspace-mcp-oauth-qa` only.** `JEV_ENABLED="true"` is written into the generated QA config by the **credential-free** job, before the artifact is built — so the flag is inside what the SHA-256 manifest covers, rather than something the credentialed job adds afterwards and the digest cannot see. The committed Wrangler templates, `staging.yml`, `deploy.yml` and the generator carry no trace of it, so production and the `a`/`b`/`c` copies cannot inherit it; tests assert all five.
- **`TYPESAFE_API_KEY` is installed as a Worker secret by one step that holds it and nothing else.** It is piped to `wrangler secret put` on stdin — never an argument, which a process listing would show — never echoed, and never written to an output, an artifact, the manifest or the provenance record. The job that runs the dispatcher's chosen code never sees it at all. A Worker secret survives redeploys, so the step is a no-op after the first run.
- **A flag without a key fails the run.** `/health`'s `jevEnabled` and `jevConfigured` are read, reported in the job summary and gated on: a QA worker that comes up with the path enabled and no key would answer every selection deterministically while looking like it was doing more, which is the one state that would quietly invalidate an A/B. Both are booleans about the key; no part of it is read or printed.
- Exact-SHA `ref`, reviewed-branch containment, the digest verification and the `--no-bundle` publish are unchanged, and the tests that pin them are re-asserted in the new block so this change cannot erode them.

### A dedicated QA worker for the Claude-chat connector

- **`.github/workflows/qa.yml`** deploys `google-workspace-mcp-oauth-qa`: the same code as production, its own worker name (so its own Durable Object namespace), its own `OAUTH_KV` namespace created through the Cloudflare API when missing, and its own rate-limit namespace id. It reuses `scripts/staging-config.mjs`, so the generator's refusals apply unchanged — it can never be pointed at production's namespace.
- **The suffix is fixed at `qa`, and that is the point.** `Staging` takes a *list* of suffixes, so a mistyped dispatch there reaches the `a`/`b`/`c` copies another workstream is testing against. This workflow cannot name them; a test asserts the file does not contain those worker names at all.
- **No production-parity gate.** `Staging` fails unless the deployed worker's version and tool count equal production's, which is the opposite of what a QA environment is for — it exists to run a build production does not have yet. This workflow gates on liveness instead (HTTP 200, `mode=oauth`, `configured=true`) and reports the version, tool count and source SHA as evidence.
- **The `ref` input is required, has no default, and must be an immutable, reviewed commit.** It is rejected unless it is a 40-character lowercase commit id — a branch or tag name can be moved between the moment it is validated and the moment it is checked out — and unless that commit is contained in `main` or a `release/*` branch, so the workflow cannot be used to run unreviewed code with deployment credentials.
- **The dispatcher's code and the credentials never share a job, and neither do the build and the deploy.** A `verify` job that references no secret at all resolves the commit, checks it out, runs `npm ci`, the typecheck, the tests and the bundle, and publishes the built Worker module, its Wrangler config, a provenance record and a SHA-256 manifest as an artifact. The `deploy` job never checks out the selected commit, never installs the project's dependencies and never bundles: it verifies every digest against the manifest and the manifest against the digest `verify` reported, installs only the one pinned Wrangler release that built the artifact (`--ignore-scripts`, nothing from the commit being deployed), and publishes that exact module with `--no-bundle`. `CLOUDFLARE_API_TOKEN` / `CLOUDFLARE_ACCOUNT_ID` and the Google credentials are mapped onto the individual steps that need them rather than onto the job, and the only change the credentialed job may make to the reviewed config is the KV namespace id it alone can look up — which is itself refused if it is production's. `contents: read` bounds the `GITHUB_TOKEN`; it does nothing for repository secrets, so the scoping has to be explicit.
- After deploying, it runs `scripts/smoke.mjs` against the QA worker — the same connector path a claude.ai client walks: the `401` advertising `resource_metadata`, the authorization-server metadata with PKCE S256, the protected-resource metadata, dynamic client registration and the consent page.

### Licence, and no deployment-specific values in the tree
- **`LICENSE`** — MIT, and `"license": "MIT"` in `package.json`. The project had no licence file, which leaves anyone reading it with no permission to use it.
- **The Wrangler configs are now templates.** `wrangler.jsonc` and `wrangler.oauth.jsonc` carry `REPLACE_WITH_YOUR_TOKEN_KV_ID` / `REPLACE_WITH_YOUR_OAUTH_KV_ID` and `ALLOWED_EMAILS: "you@example.com"` instead of one deployment's namespace ids and addresses, with the comments written for whoever clones this rather than for its original operator.
